## C1 — CRITICAL: any student could make themselves admin

**Was:** `profiles` had `UPDATE` granted directly to the `authenticated`
role, plus an RLS policy (`profiles_update_self`) that only checked
`auth.uid() = id`. Postgres RLS has no column-level enforcement, so any
signed-in user could send a raw PostgREST request —
`supabase.from('profiles').update({role: 'admin'}).eq('id', myId)` — from
devtools or curl (bypassing the app entirely) and it succeeded. Verified
exploitable against a real student account (rolled back, no account changed).

**Now:** `profiles` is `SELECT`-only for `authenticated` (matching every
other table in this project — writes go through security-definer RPCs). The
`UPDATE` grant and the `profiles_update_self` policy are removed. New
profile rows still come from the `handle_new_user` trigger; the app only
ever *reads* `profiles`, so nothing breaks.

**Verified:** re-ran the exploit → now returns `42501: permission denied for
table profiles`.

**Test on-device:**
1. Log in as a student, use the app normally — profile still displays,
   directory search still works (these are reads).
2. Log in as staff/admin — creating accounts still works
   (that path uses the service role, unaffected).
3. (Optional, to confirm the hole is closed) In Chrome devtools console on
   the running web app:
   ```js
   await supabase.from('profiles').update({role:'admin'}).eq('id', (await supabase.auth.getUser()).data.user.id)
   ```
   — should return an error, not success.

**Follow-up if you ever add an "edit my profile" screen:** add a
`security definer` RPC that whitelists `name` / `rfid_uid` only — never
re-grant a raw `UPDATE`.

## H1 — Rescheduling a class that already happened silently voided attendance

**Was:** `create_schedule_exception` only refused a change if an *exception
row* was already referenced by a `class_sessions` row (FK catch). But a
class started straight off its recurring slot has no exception row — so
moving/cancelling that occurrence afterwards was allowed, and
`calculate_course_attendance_hours` then dropped it from every enrolled
student's totals, quietly erasing scans already taken. No warning, no audit.

**Now:** before applying a move/cancel, it checks for a `class_sessions` row
on that `schedule_id + original_date` and refuses with *"This class has
already been held — its schedule can no longer be changed."* A reschedule
requested while the class is still in the future has no session yet, so it's
unaffected.

**Verified:** function body contains the new guard.

**Test on-device:**
1. As a lecturer, start a class from the timetable, have a student (or your
   test student account) check in, then end the session.
2. As that lecturer (or admin), try to **cancel or move that same past
   occurrence** from the timetable calendar → should be refused with the
   "already been held" message.
3. Now pick a **future** occurrence of a recurring class and
   move/cancel it → should still work normally.
4. As a lecturer, submit a reschedule *request* for a future class, have
   admin approve it → still works. Then repeat for a class that has since
   been held → admin's approval should fail with "Could not apply the
   change: This class has already been held…".

## H2 — Double-scan / manual-mark race threw a raw DB error

**Was:** `submit_attendance` did `SELECT` (already checked in?) then a
separate `INSERT`, with no conflict handling. A fast double-tap, or a
lecturer's manual mark landing between the two, hit the
`unique(session_id, student_id)` constraint and surfaced a raw Postgres
error to the student instead of a clean result.

**Now:** the insert is `ON CONFLICT (session_id, student_id) DO NOTHING`; if
it's suppressed, it re-reads the existing row and returns the normal
"already checked in" response (same as `set_attendance_status` already did).

**Verified:** function body contains `on conflict (session_id, student_id)
do nothing`.

**Test on-device:**
1. As a student in a live class, scan the QR and **tap the confirm button
   twice quickly** → both should resolve to "checked in" / "already checked
   in", never an error screen.
2. Have the student scan in, then immediately have the lecturer manually
   mark that same student (present/late/absent) on the Manage Attendance
   screen → no error, the manual status wins.
3. Normal single check-in still records correctly and shows in the live
   roster.

## H3 — "1 active parking reservation" cap could be raced

**Was:** the cap was only a `SELECT ... EXISTS` check inside
`book_parking_slot`. Two concurrent calls (double-tap, retry-on-timeout,
two devices) could both pass it before either inserted → a student ends up
with 2+ active reservations, defeating the cap.

**Now:** a partial unique index
`parking_reservations_one_active_per_user ON (user_id) WHERE status =
'reserved'` is the real backstop; `book_parking_slot` catches its violation
and returns the same friendly "you already have a reservation" message.

**Verified:** index exists; function catches `unique_violation`.
Pre-flight confirmed no existing user had >1 active reservation (index
built cleanly).

**Test on-device:**
1. As a student with no active reservation, book a slot → succeeds.
2. Immediately try to book a second → "You already have an active or
   upcoming reservation…" (this was already the behaviour; confirm it still
   is).
3. Cancel it, book again → succeeds (confirms the index doesn't block
   legitimate re-booking after the old row leaves `reserved`).
4. (Hard to trigger by hand) The race itself: rapidly double-tap the final
   "Confirm booking" button — you should never end up with two active
   reservations on the dashboard.

## H4 — A lecturer could tamper with any column of their own session

**Was:** `class_sessions` had table-wide `INSERT, UPDATE` granted to
`authenticated`, and the update RLS policy only checked
`lecturer_id = auth.uid()` (row scope, no column limit) — while `SELECT`
was deliberately column-restricted to hide `dynamic_qr_seed`. So a tampered
client owning a session could `PATCH` `course_id`, `room_id`,
`qr_interval_seconds`, `schedule_id`, `dynamic_qr_seed`, etc., bypassing all
of `start_scheduled_session`'s validation.

**Now:** `UPDATE` is column-restricted to `(status, end_time)` — exactly
what `endSession()` touches. Everything else is created/managed only through
the `start_scheduled_session` security-definer RPC. (`INSERT` left broad for
now — it's gated by the `class_sessions_insert_staff` policy requiring staff
role; noted as a lower-priority follow-up.)

**Verified:** `has_column_privilege('authenticated', …)` →
`status`/`end_time` = true, `course_id`/`dynamic_qr_seed` = false.

**Test on-device:**
1. As a lecturer, start a class, run it, then **end the session** from the
   app → still works (only touches status + end_time).
2. Resume an ended session by tapping its slot again → still works (that's
   the `start_scheduled_session` RPC, unaffected).
3. Starting a new scheduled session, the live QR, and student check-ins →
   all unchanged.
